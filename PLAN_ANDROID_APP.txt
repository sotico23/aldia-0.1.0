1. ANALISIS DEL SISTEMA ACTUAL (ALDIA)
============================================================

El sistema Aldia es una aplicacion Laravel 12 que maneja:

* Gestion de Pedidos y Ventas: Sistemas de ventas marketplaces,
  pedidos, facturacion, ERP sync automatico

* Logistica y Entregas: Asignacion de zonas, repartidores,
  rutas de entrega, capacidad por zona/repartidor

* Integracion con ERP: Sincronizacion automatica de pedidos a
  sistemas contables (Ventas, Tesoreria, Contabilidad, Inventario)

* Telegram Bot: Notificaciones, autenticacion, callbacks

* Frontend: InertiaJS v2 (React) para renderizado cliente-servidor

* Arquitectura: Multi-tenant con scopes OwnerScope, roles y permisos

3. COMPONENTES PRINCIPALES DE LA APP ANDROID
============================================================

3.1 MODULO DE AUTENTICACION
----------------------------
* Login con Telegram (OAuth2/WebApp Bot)
* Login tradicional email/password (Sanctum tokens)
* Registro de nuevos vendedores/clientes
* Recuperacion de contrasena
* Gestion de sesiones y refresh tokens
* Biometria (huella/FaceID) para acceso rapido

3.2 DASHBOARD PRINCIPAL
------------------------
* Resumen de pedidos pendientes/preparando/enviados/entregados
* Estadisticas en tiempo real (ventas del dia, entregas activas)
* Alertas y notificaciones push
* Acceso rapido a acciones frecuentes
* Filtros por fecha, estado, zona, repartidor

3.3 GESTION DE PEDIDOS
-----------------------
* Listado paginado con filtros avanzados
* Detalle completo de pedido (items, cliente, totales)
* Creacion de nuevos pedidos (si es vendedor)
* Cambio de estado: pendiente -> preparando -> enviado -> entregado
* Sincronizacion manual con ERP
* Historial de cambios de estado (PedidoStatusLog)
* Notas internas y comunicacion con cliente

3.4 PANEL DE LOGISTICA Y ENTREGAS
----------------------------------
* Mapa interactivo (Google Maps SDK) con:
  - Zonas de entrega (poligonos/circulos)
  - Ubicacion actual de repartidores
  - Pedidos en pool sin asignar
  - Pedidos asignados en ruta
* Asignacion automatica (usando algoritmo ZoneAssignment)
* Asignacion manual por administrador
* Seguimiento en tiempo real de repartidor
* Gestion de capacidad por zona y repartidor
* Cooldown y bloqueos de pool

3.5 GESTION DE REPARTIDORES
----------------------------
* Lista de repartidores por estado (disponible, ocupado, offline)
* Perfil completo: capacidad_max, radio_km, zona asignada
* Ubicacion actual (lat/lng) con actualizacion periodica
* Historial de entregas completadas
* Metricas de performance (tiempo promedio, calificaciones)

3.6 CONFIGURACION Y ADMINISTRACION
-----------------------------------
* Configuracion de zonas (radio, capacidad_max, poligono)
* Configuracion de DeliveryConfig (modo manual/automatico)
* Gestion de usuarios y roles
* Configuracion de notificaciones (Telegram, FCM, Email)
* Webhooks y callbacks para integraciones externas

6. FLUJOS CRITICOS DE INTEGRACION
============================================================

FLUJO 1: CREACION Y ASIGNACION DE PEDIDO
-----------------------------------------
1. Vendedor crea pedido en App Android
2. POST /api/v1/pedidos -> Laravel valida y guarda
3. Job/Listener detecta nuevo pedido -> entra a pool
4. ZoneAssignment::assignPending() ejecuta (scheduler/cron)
5. Pedido asignado a zona + repartidor optimo
6. Evento DeliveryOrderPoolUpdated -> Broadcast (Reverb)
7. App Android recibe push/websocket -> Actualiza UI
8. Notificacion Telegram al repartidor asignado
9. Repartidor acepta -> estado "preparando" -> "enviado"

FLUJO 2: SINCRONIZACION ERP
----------------------------
1. Pedido marcado como "entregado" o "pagado"
2. POST /api/v1/pedidos/{id}/sync-erp
3. ErpSyncTrait::syncPedidoToErp() ejecuta en transaction:
   - Valida stock (Inventario)
   - Crea Cliente si no existe
   - Crea Venta + DetalleVenta
   - Registra InventoryMovement (EGRESO)
   - Crea registro Tesoreria (ingreso)
   - Crea Asiento Contable
   - Marca pedido.erp_synced_at
4. Respuesta exitosa -> Notificacion al vendedor

FLUJO 3: TRACKING EN TIEMPO REAL
---------------------------------
1. Repartidor abre app -> habilita location updates
2. Cada 30s: PATCH /api/v1/repartidores/{id}/ubicacion
3. Laravel actualiza Repartidor.lat/lng
4. Frontend (Web/Android) escucha canal presence-repartidor.{id}
5. Mapa actualiza marker en tiempo real
6. Cliente puede ver ubicacion del repartidor (si habilitado)

FLUJO 4: NOTIFICACIONES TELEGRAM
---------------------------------
1. Evento en Laravel (pedido asignado, estado cambiado, etc.)
2. NotificationHelper::send() -> DeliveryPedidoAceptadoNotification
3. Canal Telegram envia mensaje formateado
4. Usuario recibe en Telegram Bot
5. Botones inline para acciones rapidas (Ver, Aceptar, Rechazar)
6. Callback query -> POST /api/v1/telegram/callback
7. Laravel procesa accion -> Actualiza estado -> Respuesta

10. CONSIDERACIONES TECNICAS ESPECIFICAS
============================================================

OFFLINE-FIRST
-------------
* Room como source of truth local
* Repository pattern: Local -> Remote -> Merge
* WorkManager para sync periodica (cada 15min)
* Cola de operaciones pendientes (dirty flags)
* Conflict resolution: Server wins (con timestamp)

TIEMPO REAL
-----------
* Laravel Reverb (WebSockets) para updates instantaneos
* Canales privados: private-pedido.{id}, private-repartidor.{id}
* Canales de presencia: presence-zona.{id}
* Reconexion automatica con backoff exponencial
* Fallback a polling si WebSocket falla

PERFORMANCE
-----------
* Paginacion cursor-based en listas grandes
* Imagenes: WebP, thumbnails, lazy loading
* Compose: keys estables, derivedStateOf, lazy lists
* Network: Compression (gzip), caching headers
* Database: Indices en owner_id, estado, fecha

TESTING
-------
* Unit: ViewModels, UseCases, Repository (MockK)
* Integration: API client con MockWebServer
* UI: Compose Testing (semanticas, screenshots)
* E2E: Dispositivos reales + Firebase Test Lab
* Arch: ArchUnit para validar capas Clean Architecture

11. RIESGOS Y MITIGACIONES
============================================================

| Riesgo                                    | Probabilidad | Impacto | Mitigacion                              |
|-------------------------------------------|--------------|---------|-----------------------------------------|
| Cambios breaking en API Laravel           | Media        | Alto    | Versionado API (/v1/), tests contract   |
| Limites Google Maps API (costos)          | Media        | Medio   | Caching, clustering, limites diarios    |
| Problemas conectividad repartidores       | Alta         | Alto    | Offline-first, sync diferido            |
| Complejidad algoritmos asignacion         | Media        | Medio   | Tests unitarios exhaustivos, logging    |
| Adopcion usuarios (repartidores)          | Media        | Alto    | UX simple, training, soporte dedicado   |
| Seguridad datos ubicacion (privacidad)    | Baja         | Critico | Consentimiento, anonimizacion, retencion|
