PARTE 1: CONTEXTO Y ESTADO ACTUAL
================================================================================

MODELO DE NEGOCIO ACTUAL
  - SaaS multi-tenant: cada negocio (owner_id) tiene sus usuarios, ventas,
    pedidos e inventario. Aislamiento via OwnerScope (Master/Super Admin
    hacen bypass).
  - Pedidos (tabla pedidos): estados pendiente -> confirmado -> preparando
    -> enviado -> entregado -> cancelado. Solo direccion_cliente (texto
    libre). NO tienen lat/lng ni repartidor asignado.
  - Ventas (tabla ventas): flujo ERP + Entrega (flota) ligada a la venta
    (no al pedido).
  - Modulo Flota (back-office): vehiculos (con lat/lng + IMEI + tracking),
    conductores (modelo propio, SIN login), entregas, cargas diarias
    (autoventa B2B en ruta), grupos de trabajo.
  - Tracking: POST /api/v1/tracking/update actualiza vehiculos.lat/lng por
    IMEI (dispositivo GPS externo). No hay historico de posiciones.
  - Chat por pedido: conversaciones creadas automaticamente al hacer el
    pedido (comprador <-> vendedor), con Reverb (Pusher).
  - Roles (Spatie + nivel): Master(0), Super Admin(1), Administrador(2),
    Empleado(3), Cliente(3), Proveedor(3), Usuario(3). NO existe rol
    Repartidor.
  - Notificaciones: database + mail (Laravel Notifications). NO hay push
    (sin FCM, sin Web Push). Telegram/WhatsApp directo via N8nService.
  - NO existe app movil ni PWA. Mapas: componente MapaVehiculos
    (@react-google-maps/api) con VITE_GOOGLE_MAPS_API_KEY.

QUE FALTA PARA UN MODELO TIPO UBER EATS / RAPPI / GLOVO
  1. Rol repartidor con login (hoy los conductores no inician sesion).
  2. Geolocalizacion del destino: pedidos y clientes sin lat/lng.
  3. Tabla de posiciones en vivo del repartidor + broadcast en tiempo real.
  4. Vinculacion explicita pedido <-> repartidor (hoy la entrega depende
     de la venta y solo si su numero empieza con 'PEDIDO-').
  5. Pool de pedidos con aceptacion/rechazo y timeout de re-asignacion.
  6. Notificaciones push al repartidor (Web Push + Telegram fallback).
  7. PWA movil para el repartidor + zona admin con mapa en vivo.

DECISIONES TOMADAS (2026-08-11)
  - Plataforma: PWA web movil ahora; arquitectura API-first para que una
    app nativa (React Native/Expo) se conecte despues sin rehacer backend.
  - Alcance: SOLO delivery B2C (pedidos de tienda/marketplace entregados
    al consumidor final). No incluye rutas B2B ni autoventa.
  - Asignacion: AMBOS modos configurables por negocio:
      pool + aceptacion (estilo Rappi) y asignacion manual por admin.
  - Notificaciones: Web Push (VAPID, gratis) + bot de Telegram existente
    como fallback. Sin Firebase por ahora.

================================================================================
PARTE 2: ARQUITECTURA OBJETIVO
================================================================================

  Repartidor (PWA movil) --API sanctum--> /api/v1/delivery/* --> Laravel
  Admin/vendedor (web React) --mapa en vivo--> Reverb canal privado
      delivery.{owner_id}.positions y delivery.{owner_id}.orders
  Web Push (VAPID) + Telegram bot --> notifican al repartidor
  Google Geocoding API --> geocodifica direccion_cliente -> lat/lng

FLUJO DE REPARTO (pool)
  checkout (lat/lng destino) -> pendiente -> confirmado -> preparando
    -> [entra al pool] -> repartidor acepta (lockForUpdate) -> enviado
    -> entregado / cancelado
  El enum de pedidos NO cambia: hora_aceptado marca el punto intermedio.

PARTE 5: RIESGOS Y MITIGACIONES
================================================================================
  1. Google Geocoding requiere billing -> fallback manual en mapa y cache;
     si falla la geocodificacion el pedido entra al pool solo si el
     vendedor ubica el destino (o con coords null y distancia calculada
     por el repartidor en aceptacion).
  2. Doble aceptacion del mismo pedido -> lockForUpdate + transaccion +
     verificacion de repartidor_id null dentro de la transaccion.
  3. Repartidor offline con pedido aceptado -> timeout de recogida
     (Fase 6) re-publique y bloquee aceptacion si last_position_at > 10min.
  4. Web Push exige HTTPS -> ok (aldiaproyect.com cumple).
  5. Reverb caido -> GPS y pool siguen funcionando por polling; solo se
     pierde la vista en vivo (UI degrada a refresh manual).
