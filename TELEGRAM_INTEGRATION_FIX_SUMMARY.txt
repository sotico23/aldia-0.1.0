TELEGRAM INTEGRATION FIX SUMMARY
================================
Proyecto: aldia-0.1.0-main
Fecha: 2026-08-02
Autor: Revisión y correcciones de integración Telegram + n8n

OBJETIVO
--------
Solucionar el problema crítico: "el chat_id y el campo used_at no se están enviando o
persistiendo correctamente durante el flujo del webhook y el proxy", y el error 422
recibido en el navegador al probar la conexión de Telegram desde
Index.tsx (POST /configuracion-web/test-telegram 422).

FLUJO DE DATOS (Telegram -> Laravel -> n8n)
------------------------------------------
1. Telegram envía el update a POST /webhooks/telegram (Laravel) — ruta pública (verificado
   routes/web.php:362). La llamada al bot se configura en ChannelCredentialController::update
   (setWebhook(route('webhooks.telegram'))).
2. TelegramWebhookController::handle -> TelegramWebhookService::processWebhook:
   - extrae chat_id de message.chat.id / callback_query.message.chat.id / from.id
   - si text === "/start TOKEN" -> linkAccount: persiste telegram_chat_id + used_at
     en telegram_linking_tokens y ChannelCredential (transacción DB).
   - si mensaje normal -> buildPayload (incluye chat_id) -> forwardToN8n -> HTTP POST
     a N8N_TELEGRAM_PROXY_URL (default https://n8n.redcliente.cl/webhook/telegram-proxy).
3. n8n recibe el payload con chat_id e intenta propagarlo. Si el workflow "telegram-proxy"
   no está activo en n8n, devuelve 404 y el mensaje se pierde.
4. Login Widget -> POST /telegram/login-callback -> TelegramCallbackController: valida hash
   HMAC-SHA256 con el bot_token y marca used_at del token de vinculación.

PROBLEMAS ENCONTRADOS
---------------------
P1. (browser 422) WebSettingController::testTelegramConnection usaba Http::get() plano
    (sin timeout/connectTimeout/verify=>false). Los logs mostraban:
        testing.ERROR: Telegram connection test exception {"error":"Network error"}
    repetido al pulsar "Probar Conexión". La excepción se atrapaba y devolvía 422 con el
    mensaje engañoso "El Token de Telegram ingresado no es válido o expiró." aunque el
    token fuera correcto. Causa: falla la verificación SSL / conexión saliente en el
    entorno local, algo que TelegramService::validateCredentials ya manejaba con
    Http::timeout(10)->connectTimeout(5)->withOptions(['verify' => false]).
P2. (chat_id) callback_query: chat_id se extraía de $message['chat']['id'], pero en un
    callback_query el chat está en $message['message']['chat']['id'] -> null -> early
    return: chat_id perdido, nada se reenvía ni persiste.
P3. (chat_id) body envuelto como STRING JSON (p. ej. n8n reenvía {"body": "{...}"}):
    $update quedaba como string y $update['message'] lanzaba TypeError -> try/catch ->
    ['status' => 'ok'] -> el update (incl. vinculación) se perdía silenciosamente.
P4. (used_at) TelegramCallbackController: el Telegram Login Widget NO envía "token", por
    lo que se usaba el fallback del "último token activo del usuario", que podía marcar el
    token equivocado. Además, si en el futuro se incluía "token" en el body, el cálculo
    del hash firmado por Telegram incluiría "token" -> hash inválido -> vinculación fallida.
P5. (used_at) fallback no usaba el scope valid() (tampoco verificaba expiración) y no
    estaba dentro de transacción junto a la credencial.
P6. (n8n 404) forwardToN8n: el webhook n8n redirigía a https://n8n.redcliente.cl/webhook/
    telegram-proxy que devolvía 404 "The requested webhook POST telegram-proxy is not
    registered." porque el workflow "telegram-proxy" no está activo en n8n. (Esto es
    configuración de infraestructura n8n: hay que activar el workflow.)

CAMBIOS APLICADOS — V2 (vinculación /start TOKEN vs Login Widget)
---------------------------------------------------------------
Motivo: el comando /start llegaba limpio al bot sin el token de vinculación, y por
eso chat_id y used_at no se actualizaban. Análisis de los 4 escenarios:

B1. (root cause - UX) t.me/{bot}?start=TOKEN: en Telegram, el payload ?start= solo se
    envía cuando el usuario pulsa START Y el chat aún no está iniciado. Si el bot ya
    fue iniciado, el enlace abre el chat SIN enviar el payload -> el usuario pulsa
    "Iniciar" manualmente y llega /start limpio -> onboarding "¡Hola!" -> el token
    nunca viaja -> chat_id/used_at no se persisten.
B2. (root cause - frontend) ChannelCredentials -> openChatWithLinking hacía
    `await generateLinking()` (fetch async) y luego `window.open`: el bloqueador de
    popups lo anulaba -> el enlace nunca se abría solo -> el usuario abría el chat manualmente.
B3. (root cause - token burn) El Login Widget ("Iniciar Sesión con Telegram") y el
    flujo de chat ("Abrir Chat en Telegram") convivían en la misma página. El callback
    del widget (TelegramCallbackController) marcaba used_at del "último token activo del
    usuario logueado" como fallback -> QUEMABA el token generado para el enlace de chat;
    al pulsar /start TOKEN en el chat el token ya estaba usado -> "❌ token inválido o
    expirado". used_at/chat_id quedaban inconsistentes.
B4. (UI) En modo global, el botón "Abrir Chat en Telegram" estaba oculto (requería
    telegramStatus==='success', que nunca ocurre en modo global).

CORRECCIONES V2
--------------
app/Http/Controllers/Backend/TelegramCallbackController.php
   - SE ELIMINA el fallback que marcaba used_at del último token activo (ramas `elseif
     (Auth::check())`). El widget web solo actualiza ChannelCredential.telegram_chat_id
     + telegram_linked_at; los tokens los consume exclusivamente el webhook /start.
     Así el widget ya no "quema" tokens y el flujo de chat vuelve a ser el único dueño
     del ciclo used_at. Se mantiene la actualización del chat_id con el uid del widget
     (válido como chat_id en chats privados).

app/Services/TelegramWebhookService.php (linkAccount)
   - Idempotente ante re-entregas de Telegram: si el token ya está usado pero con el
     MISMO telegram_chat_id, se devuelve ['status'=>'linked'] (antes: "❌ token inválido").
     Consulta el token SIN el scope valid() y valida usado/expiración explícitamente, de
     modo que el caso de re-entrega no rompa la vinculación ni marque used_at dos veces.

app/Http/Controllers/Backend/TelegramLinkingController.php
   - generateLink devuelve ahora `token` en el JSON (además de telegram_url) para que
     el frontend permita pegar /start TOKEN manualmente.

resources/js/pages/Backend/ChannelCredentials.tsx
   - openChatWithLinking abre la ventana SINCRÓNICAMENTE (window.open(''), luego
     win.location.href = url) -> evita el popup blocker.
   - Tras generar el enlace, se muestra el token con "/start {token}" + botón de copiar
     (clipboard) -> fallback fiabilidad UX: si Telegram descarta el payload, el usuario
     pega /start TOKEN a mano.
   - Modo global: "Abrir Chat en Telegram" ahora se muestra cuando
     global_telegram_bot_username existe (no depende de telegramStatus).
   - La tarjeta del Login Widget aclara que es login web opcional y NO vincula el canal.

=== V3 — RAZÓN RAÍZ: BOT GLOBAL SIN WEBHOOK + TOKENS FANTASMA ===
------------------------------------------------------------
Síntoma: el chat_id y used_at seguían quedando NULL aunque el widget y el
/start TOKEN parecieran bien; y telegram_linking_tokens acumulaba filas
"usadas-at=NULL" (id=55: owner_id=5, user_id=1, bot_type=global) que nunca
se consumían.

RC1. (bot global sin webhook) El webhook del bot GLOBAL nunca se configuraba:
     - ChannelCredentialController::update setea setWebhook SOLO para el bot
       CUSTOM al guardar (verificado routes/web.php:362 + controlador).
     - WebSettingController::testTelegramConnection llamaba a getMe
       (TelegramService::validateCredentials) pero NO llamaba a setWebhook,
       por lo que probar la conexión no dejaba al bot escuchando.
   Conclusión: un bot admite un único webhook -> "setWebhook apuntando a Laravel"
   (POST /webhooks/telegram) y "Telegram Trigger de n8n" son mutuamente
   excluyentes para el MISMO bot. Elegir topología:

     TOPOLOGÍA A (elegida): Telegram -> POST /webhooks/telegram (Laravel)
       -> processUpdate -> linkAccount / forwardToN8n.
       n8n solo como PROXY de SALIDA (telegram-proxy), recibe chat_id ya
       resuelto desde Laravel. Ventaja: el deep link /start TOKEN llega
       directamente a Laravel y persiste chat_id + used_at en la transacción.
     TOPOLOGÍA B (respaldo): Telegram -> Telegram Trigger (n8n)
       -> HTTP Request -> POST /api/canales/telegram/webhook (Laravel).
       Se incluye workflow importable docs/n8n/telegram-inbound.json, activado
       SOLO si el webhook del bot apunta a n8n (no con Topología A).

RC2. (tokens "fantasma") N8nService::testConnection CREABA un
     TelegramLinkingToken en cada "Probar conexión" (solo para renderizar el
     link de prueba), dejando filas usadas-at/chat_id=NULL que confundían
     los reportes y el scope valid(). Corrección: testConnection reutiliza el
     token valid() existente (más reciente) y envía linking_url=null si no
     hay uno; la creación de tokens es responsabilidad EXCLUSIVA del flujo
     /start deep-link (TelegramLinkingController::generateLink).
