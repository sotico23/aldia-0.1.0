1. CONTEXTO DEL PROYECTO
================================================================================

3. LO COMPLETADO (2): CAPA BOT API /api/v1/bot (MODULO CLIENTES)
================================================================================
Objetivo: exponer CRUD de la plataforma a un agente IA (n8n) con aislamiento
multi-tenant ESTRICTO y respuestas JSON pensadas para LLM.

Archivos nuevos:
- app/Support/BotContext.php
  Value object inmutable (ownerId, actingUserId) del request actual.
- app/Http/Middleware/Bot/ResolveBotTenant.php  (alias: bot-api)
  Autenticacion + resolucion de tenant:
  * Authorization: Bearer <api_token>  -> User::where('api_token', ...)
  * X-Owner-ID obligatorio y numerico.
  * Si la key es de Master/Super Admin: NO se hace bypass, el contexto se
    resuelve SIEMPRE al tenant indicado en X-Owner-ID.
  * Si la key es de un usuario normal: X-Owner-ID debe coincidir con
    getOwnerId() del usuario.
  * X-User-ID opcional: debe existir, estar activo y pertenecer al tenant
    (se usa como auditoria / user_id en creaciones).
  * Auth::setUser(tenant) -> activa OwnerScope y auto-asignacion de owner_id.
- app/Http/Controllers/Api/Bot/BotBaseController.php
  Helpers: ok(), created(), notFound(), error() con contrato
  {status, message, data?, errors?}.
- app/Http/Controllers/Api/Bot/ClienteBotController.php
- app/Http/Requests/Api/Bot/StoreClienteRequest.php
- app/Http/Requests/Api/Bot/UpdateClienteRequest.php
  Validacion: nombre required; email unico GLOBAL (ver seccion 7); rut/nit
  unicos POR TENANT; categoria_id debe existir y pertenecer al tenant.
- app/Services/Api/Bot/ClienteBotService.php
  paginate (search agrupado, filtro activo, limit<=100, offset), find con
  where('owner_id') explicito (defensa en profundidad), create (setea
  user_id=actingUserId y owner_id), update, disable (activo=false),
  serialize (payload LLM, sin campos tecnicos).
- app/Support/OpenApi/BotOpenApi.php
  Documento OpenAPI 3.1 generado en codigo (sin dependencias) para importar
  en n8n como "Tools via OpenAPI".
- app/Http/Controllers/Api/Bot/OpenApiController.php
  GET /api/v1/bot/openapi (publico, no expone datos).

Archivos modificados:
- routes/api.php: grupo Route::prefix('v1/bot')->middleware(['bot-api',
  'throttle:bot']) con 5 endpoints de clientes + openapi fuera del grupo.
- bootstrap/app.php:
  * alias 'bot-api' => ResolveBotTenant::class
  * withExceptions: ModelNotFoundException -> 404 y ValidationException ->
    422 con contrato JSON SOLO para rutas api/v1/bot/*.
- app/Providers/AppServiceProvider.php:
  RateLimiter::for('bot', Limit::perMinute(120)->by(X-Owner-ID|ip)).
- app/Services/ClienteService.php:
  FIX DE SEGURIDAD: buscarClientes() usaba orWhere sin agrupar, lo que
  generaba WHERE owner_id = X AND nombre LIKE ... OR nit LIKE ... -> las
  clausulas OR escapaban el filtro de tenant (fuga cross-tenant). Ahora el
  where se agrupa en un closure.

Endpoints activos (php artisan route:list --path=v1/bot):
  GET    api/v1/bot/clientes          -> listar (search, activo, limit, offset)
  POST   api/v1/bot/clientes          -> crear (201)
  GET    api/v1/bot/clientes/{cliente}-> detalle
  PUT    api/v1/bot/clientes/{cliente}-> actualizar (parcial)
  DELETE api/v1/bot/clientes/{cliente}-> desactivar (activo=false, reversible)
  GET    api/v1/bot/openapi           -> especificacion OpenAPI 3.1

5. CONTRATO JSON PARA LLM/n8n
================================================================================
Exito:
  { "status": "success", "message": "Clientes obtenidos.",
    "data": { "items": [ { "id": 1, "nombre": "...", "rut": null, ... } ],
               "total": 1, "limit": 50, "offset": 0 } }

Creado (201):
  { "status": "success", "message": "Cliente creado.", "data": { ... } }

Error validacion (422):
  { "status": "error", "message": "Datos invalidos.",
    "errors": { "email": ["El campo correo electronico ya ha sido registrado."] } }

No encontrado (404):
  { "status": "error", "message": "Cliente no encontrado.", "errors": [] }

Auth (401): token faltante/invalido, X-Owner-ID faltante, token-tenant
  desajustado, X-User-ID ajeno. 403: cuenta desactivada.

7. HALLAZGOS Y DECISIONES IMPORTANTES
================================================================================
- clientes.email tiene INDICE UNICO GLOBAL en BD (migracion
  2026_04_19_003221_add_unique_index_to_clientes_email.php). Consecuencia:
  la unicidad de email es GLOBAL (no por tenant). La validacion del bot
  replica la BD para no generar 500 por UniqueConstraintViolation.
  SI SE QUIERE email unico por tenant, hay que modificar esa migracion
  (crear indice compuesto owner_id+email) - requiere decision del producto
  y nueva migracion (no se hizo).
- rut/nit: sin indice unico en BD -> validacion de unicidad POR TENANT a
  nivel de Form Request (sin conflicto con la BD).
- NO existe Laravel Sanctum instalado (routes/api.php lo usa solo en
  /user y tracking con auth:sanctum, que no se toca).
- Se eligio soft-delete (activo=false) para DELETE: reversible ante errores
  del agente IA.
- OpenAPI generado a mano (sin dependencias nuevas, regla del proyecto:
  no cambiar dependencias sin aprobacion).
- El rate limiter 'bot' (120/min) usa X-Owner-ID como clave.

9. COMO CONECTAR N8N (PASO A PASO)
================================================================================
1. En n8n: crear credencial "OpenAPI" apuntando a
   https://<dominio>/api/v1/bot/openapi  (o importar el JSON del endpoint).
2. Activar "Tools via OpenAPI" para que el agente (LangChain agent) vea las
   tools: al_dia_clientes_listar, _obtener, _crear, _actualizar, _desactivar.
3. En cada Tool/HTTP Request, incluir headers:
     Authorization: Bearer <api_token_del_tenant>
     X-Owner-ID: <id_del_tenant>
     X-User-ID: <id_del_usuario>   (opcional, recomendado para auditoria)
4. Guardar el api_token del tenant en las variables de entorno de n8n
   (no en el workflow).
