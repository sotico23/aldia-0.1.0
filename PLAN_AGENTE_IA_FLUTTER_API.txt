================================================================================

AlDia es un ERP multi-tenant en Laravel 12 con 14 modulos de negocio:

  * CRM / Comercial ....... clientes, prospectos, oportunidades, productos,
                            categorias, campanas, tickets, call-center
  * Ventas / POS .......... ventas, variantes, skus, cupones, POS (cierre,
                            facturacion, promociones, reportes)
  * Inventario ............ proveedores, compras, inventarios, almacenes, lotes,
                            movimientos, vacios, inventario-cierre
  * Finanzas .............. cobranzas, pagos, tesoreria, contabilidad (asientos),
                            impuestos, facturacion, SII (DTE/CAF/folios)
  * MRP ................... boms, ordenes-produccion, calidad, planificacion
  * Proyectos ............. proyectos, hitos, timesheets, gastos-proyecto
  * RRHH .................. empleados, nominas, asistencia, reclutamiento,
                            evaluaciones, prestamos
  * Flota ................. vehiculos, conductores, entregas, cargas-diarias,
                            grupos-trabajo
  * Delivery .............. repartidores, zonas-reparto, pool, tracking
  * LMS ................... cursos, modules, lessons, quizzes
  * Admin / Plataforma .... configuracion, paises, configuracion-web, usuarios,
                            roles, permisos, reportes
  * Marketplace / Rifas ... rifas, prizes, tienda, booking
  * Uptime ................ uptime/alerts, webhooks
  * Otros (web.php) ........ appointments, servicios, cotizaciones, tareas,
                            chat/mensajes, pagos (webpay/paypal/mercadopago)

Stack: PHP 8.2+ / Laravel 12 / Inertia 2 + React / Livewire 4 / Fortify 1.30 /
Sanctum 4.3 / Spatie Permission 7 / Pest 4 / Tailwind 4 / Reverb / MySQL.

Frontend existente: Inertia+React (web). NO existe app movil.

1.1 AISLAMIENTO MULTI-TENANT (no tocar, es la base de todo)
--------------------------------------------------------------------------------

  - Trait:      App\Traits\BelongsToOwner  ->  columna owner_id
  - Scope:      App\Scopes\OwnerScope       ->  filtra owner_id = Auth::user()->getOwnerId()
  - Excepcion:  Master / Super Admin tienen BYPASS del scope (Gate::before en
                AppServiceProvider::boot()).
  - User::getOwnerId() (app/Models/User.php:243-270) sube por la cadena
    creator_id hasta la raiz. Un usuario sin creator_id es su propio tenant.
  - NO existe columna business_id en users. El tenant = raiz de la cadena creator.
  - En las rutas con token el scope es INERTE (ver hallazgo H5). Por eso el
    Bot API aplica ->where('owner_id', $ownerId) EXPLICITO en cada query:
    el scope es refuerzo, la defensa real es el filtro manual.

Roles usados en codigo: Master, Super Admin, Administrador, Usuario, Cliente,
Proveedor, Repartidor. (Role tiene columna level: 0=Master ... 3=Usuario.)

    El SERVICE LAYER es la fuente de verdad. La API HTTP es un adaptador
    delgado. El agente Laravel llama los BotService in-process (sin
    auto-llamadas HTTP ni round-trip). Un agente externo consume la misma
    API HTTP con el mismo contrato OpenAPI. Un solo contrato para todos.

    Authorization: Bearer <pat|api_token>
    X-Owner-ID: <tenant_user_id>      (obligatorio, numerico)
    X-User-ID: <acting_user_id>       (opcional, auditoria)
    Accept: application/json

5.1 OLA 1 - AUTH API (lo que consume Flutter)
--------------------------------------------------------------------------------

  Prefijo: /api/v1/auth   (routes/api.php, middleware throttle:api-auth / login)

  ENDPOINTS

    POST /api/v1/auth/login
      Body:  { "email": "...", "password": "...", "device_name": "pixel-8" }
      200 -> { "status":"success", "message":"Sesion iniciada.",
               "data": { "token": "<pat>", "token_type":"Bearer",
                         "abilities":["agent:read","reports:read"],
                         "expires_at":"2026-11-20T12:00:00Z",
                         "user": { id, name, email, telefono, direccion, country,
                                   business_name, business_logo_path,
                                   business_cover_path, is_active, created_at },
                         "tenant": { id, name, business_name } } }
      401 -> credenciales invalidas (NO revelar si el email existe)
      403 -> cuenta inactiva / bloqueada
      422 -> { "status":"error", "message":"Codigo 2FA requerido.",
               "data": { "two_factor_required": true, "challenge_id": "..." } }
      Rate limit: 5/min por email|ip (reusar RateLimiter::for('login')).

    POST /api/v1/auth/two-factor/verify
      Body: { "challenge_id":"...", "code":"123456" }
      200 -> mismo shape que login.
      (Fortify tiene 2FA habilitado con confirm+confirmPassword y NO tiene ruta
       JSON. Hay que implementar el desafio.)

    POST /api/v1/auth/refresh
      Body: { "token":"<pat actual>" }
      200 -> nuevo PAT + abilities. Revoca el PAT usado (rotacion).
      401 -> token invalido/expirado.

    POST /api/v1/auth/logout
      Header: Authorization Bearer <pat>
      200 -> revoca el PAT actual (y opcionalmente todos del device_name).

    GET /api/v1/auth/me
      Header: Authorization Bearer <pat>
      200 -> { user, tenant, abilities, modules: [...], tools_disponibles: [...] }

  ABILITIES (columna abilities de personal_access_tokens, JSON)
    agent:read        todas las tools de lectura de /api/v1/bot/* y /api/v1/agent/*
    agent:write       reservado para la Ola 6 (escritura)
    agent:admin       herramientas administrativas del tenant

13. NOTAS DE IMPLEMENTACION - OLA 0 (estado real, 2026-10-21)
================================================================================

  Ola 0 queda implementada y verificada. Desviaciones respecto del plan
  original (documentadas para que Olas 1-5 partan de la realidad):

  [1] BUSQUEDA GLOBAL -> /api/v1/global-search (no /api/global-search)
      Laravel sobrescribe las rutas con el MISMO metodo+URI, y routes/web.php
      se registra despues que routes/api.php: la ruta web gana. Por eso la
      variante para API (token) se publico bajo el prefijo v1:
        GET /api/v1/global-search?q=...   -> agent-api + ability:agent:read
      La ruta web /api/global-search (session) se mantiene intacta para el
      frontend Inertia.

  [2] config('sanctum.expiration') es un ENTERO (minutos)
      Sanctum 4.3.3 hace `now()->subMinutes($this->expiration)`: un objeto
      Carbon rompe el Guard con "Unsupported operand types: Carbon * int".
      -> .env: SANCTUM_EXPIRATION_MINUTES=43200 (30 dias).
      -> ApiTokenService::defaultExpiration() convierte los minutos a fecha
         absoluta para guardarla en `expires_at`.

  [3] ELIMINADO el trait BelongsToOwner del modelo User
      El commit corrupto 15215a2 ("laster") agrego `BelongsToOwner` al
      modelo User. Su OwnerScope filtra por `users.owner_id`, columna que es
      NULL para el owner del tenant (la jerarquia real de tenants es
      `creator_id`, ver User::getOwnerId()). Con el scope activo, cualquier
      User::find() / User::where() devolvia 0 filas para los tenants que no
      son Master/Super Admin:
        - no se notificaba al vendedor cuando un repartidor aceptaba el pedido
        - RepartidorController devolvia 404 al crear/vincular un repartidor
          y la lista de `candidatos` salia vacia
      Se restored el estado previo a 15215a2: User NO usa BelongsToOwner,
      se conserva el hook `creating` que puebla `users.owner_id` y la
      relacion `owner()`.

  [4] MarkApiRequest: deteccion de "es una peticion de API"
      routes/web.php declara rutas reales bajo /api/... (api/system-integrations/*,
      api/v1/tenant-credentials/autocomplete, api/global-search, api/sii/*)
      que deben redirigir a /login. Los renderers JSON de 401/403 ya no
      detectan la API por el prefijo de URI: usan el atributo `api_request`
      que fija el middleware MarkApiRequest (prependido al grupo `api`).

  [5] VerifyN8nApiKey acepta la clave global de n8n
      Ademas de `users.n8n_api_key`, se acepta la clave global guardada en
      `system_integrations` (provider = 'n8n', is_active = 1), que es la que
      describe el propio comentario de la ruta.

  [6] Envolvimiento de respuesta
      El envelope {status, message, data} / {status, message, errors} ya lo
      usaba el Bot API existente (BotBaseController::ok()/notFound()). Los
      endpoints NUEVOS de las Olas 1-5 deben mantener ese mismo contrato.
      Lo que NO cambia de formato son las rutas del panel web ni los
      endpoints internos de n8n (api/internal/*, api/v1/delivery/*,
      api/v1/zones/*), para no romper los workflows ya desplegados.

  [7] SUITE DE TESTS
      La suite heredada estaba rota (Pest 4, 61 fallos, modelos/eventos
      corruptos). Estado actual: suite completa en verde.
      Archivos clave reparados:
        tests/Pest.php                 -> pest()->extend(TestCase::class)
                                           ->use(RefreshDatabase::class)
                                           ->in('Feature','Unit')
        tests/TestCase.php             -> prepareDatabase() siembra paises y
                                           4 roles dentro de la transaccion
        app/Models/User.php            -> sin OwnerScope (ver [3])
        app/Http/Resources/*           -> eliminados (codigo muerto del
                                           commit corrupto, 0 referencias)
        app/Events/*                   -> 4 eventos reescritos
        database/factories/ProductoFactory.php
                                        -> 'categoria_id' => Categoria::factory()
                                           (antes era un id aleatorio 1..10 y
                                           reventaba la FK de sqlite al azar)
        tests/Feature/Internal/N8nControllerTest.php
                                        -> las citas de Appointment usaban
                                           nombres de columna inexistentes
                                           (cliente_id, servicio_id, fecha_inicio,
                                           estado) -> corregidas a las reales
                                           (client_id, producto_id, start_time,
                                           status)
      Archivos de test nuevos:
        tests/Feature/Api/Agent/AgentApiAuthTest.php  (19 tests, Ola 0)

  [8] NO se aplico `throttle:api` a todo el grupo `api`
      El plan original (O0.11) pedia `$middleware->api(append: ['throttle:api'])`.
      El limiter `api` tiene un techo de 60/min, mientras que el Bot API
      necesita 120/min: aplicarlo al grupo entero habria REDUCIDO el limite
      de las rutas de lectura existentes. Se aplico `throttle:api` solo a las
      rutas que no lo tenian (`api/user`, `api/v1/bot/openapi`) y se definieron
      limiters propios para el agente: agent-read 120/min, agent-write 30/min,
      agent-chat 20/min, api-auth 10/min.

  [9] La ability minima NO se exige dentro de ResolveAgentContext
      Se dejó como middleware independiente (`ability:agent:read` /
      `ability:agent:write`) para poder separar el grupo de lectura del de
      escritura sin duplicar la resolucion del contexto. El efecto es el
      mismo: un PAT sin abilities recibe 403 en las rutas de lectura/escritura.

  [10] `laravel/sanctum` se fijo en `^4.3` (antes `*`)
      Con `*` composer no fijaba la version y el lock podia resolver una
      mayor/menor incompatible. Sanctum 4.3.3 es la version instalada y la que
      define el contrato de `config('sanctum.expiration')` en minutos.
